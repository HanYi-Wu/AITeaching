# 组卷与 API 核心升级

基线：`319f189`（1.6.7）；实施日期：2026-10-24。

## 范围与顺序

1. 提取请求上下文、输入契约和按业务划分的 API 路由，保留现有 URL、请求结构、角色权限和部署入口。
2. 建立应用工厂，集中注册中间件、路由和分析服务依赖；业务模块不反向导入应用入口。
3. 统一 PDF / Word 导出的校验、归属检查、构建、恢复与清理流程，保持两种格式的返回结构。
4. 处理导出并发、错误状态和重复请求，提供有权限边界的任务状态与失败重试。
5. 重构组卷状态、业务规则与界面组件；加入撤销、重做及显式草稿恢复。
6. 补齐接口兼容、并发、失败和角色隔离场景，验证现有前后端行为及生产构建。
7. 整合可复用的交付核验工具，记录架构决策、迁移方式与实测成果。

## 设计约束

- 保留学校内网、本地和桌面部署方式，采用模块化单体，按实际职责划分模块。
- API 路由只负责输入输出及调用服务；请求上下文和业务服务不依赖路由或应用入口。
- 迁移代码、修改逻辑和新增能力分别记录；提交按完整的独立改动组织。
- 现有权限、教师数据隔离、模板刷新及迟到响应保护属于必须保持的行为。
- 草稿恢复按账号、项目和试卷隔离，显式恢复，不存认证令牌。
- 导出任务重试重新执行权限校验；已完成任务不会因重复操作再次发布产物。

## 验证依据

使用现有后端测试、前端测试和生产构建；新增用例覆盖用户可感知行为与故障条件。
初始前端全并发运行曾出现角色切换超时；最终现有 256 项前端测试、566 项后端测试及生产构建通过，详见[设计与验证记录](../design/2026-10-24-core-upgrade.md)。
真实 OCR、Linux 安装与跨平台构建按实际运行环境报告，不将未执行的检查写作通过。
